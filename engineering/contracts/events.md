## 1. Scope

How committed state changes and live activity reach every consumer. Emitters: `sessions` and `printer`. Transport: `server` (state fetches plus one live stream per client). Consumers: `ui` (via `server`) and `sessions` (subscribing directly to `printer`'s freshness events for the binding contract's re-derivation on every freshness change — the same *delivery* guarantees below — keyed state-bearing payloads, at-least-once, commit order, convergence — apply to every subscribed consumer, module-internal ones included, while the transport-specific guarantees (liveness, heartbeats, streams) belong to the remote path alone; this is the document that owns them, wherever the subscriber sits). Covers the event-bearing half of the architecture edges `server → sessions` and `server → printer` (the subscription `server` opens on each emitter), the direct `sessions → printer` freshness subscription, and `ui ↔ server` (fetch + stream). The cross-seam conventions (`conventions.md`) apply here, and this document owns the event and key vocabulary the conventions list.

## 2. Wire surface

- **Durable events** — one per committed mutation, each carrying its *entity key* and a *state-bearing payload*: the full content its consumers render from, never a bare changed-flag (the appended transcript entry whole, the created session's list row, the new binding state, the printer's new freshness or reachability state — a transition *to Fresh* carrying the freshly interpreted list, per the printer-state contract). The set: session created, transcript entry appended — one family covering *every* entry kind the sibling contracts commit (a user message, an agent text segment, a tool call, a tool result, a system note such as a binding trace or resume record, a failure entry), each entry individually keyed so a turn's several entries deduplicate independently (ordering stays with the stream's commit order, per §3) — evidence added (one family covering both intakes — an upload and an attached snapshot alike, each item individually keyed by its evidence identifier so back-to-back intakes deduplicate independently, carrying the new evidence entry with its provenance, so a snapshot captured via one device appears live on every other), name changed, binding changed, archive changed, camera choice changed, session deleted (the one terminal exception to state-bearing payloads: it carries the session key alone — there is no state left to bear, and consumers remove the session), session failure (announcing a persistence-failure *condition* on the session — a transcript append that cannot be persisted; the condition is part of the session's served state while it stands, so fetches and resync-refetches surface it like any other state and the universal fetched-or-replayed guarantee holds with no carve-out; the payload and the fetched condition alike carry the session key, the key of *every* affected entry — localizing each piece of stuck content within its turn, however many stand at once — and the cause, cause-naming per R10; the event fires on every change to the condition's key-set — its first standing, each further entry joining, and its clearing per the message-lifecycle contract's clearing rule — with the state-bearing payload always carrying the full current set, empty at clearing, so a connected device is never silently stale about what is stuck and the state-bearing rule holds with no second exception), printer reachability changed (keyed per printer, its state-bearing payload carrying the new reachability state — with its cause exactly when the state carries one, Unreachable; the other states are causeless, and Reachable's retained last failure is diagnosis, not a cause), printer freshness changed — keyed to the singleton *printer-knowledge* entity, since freshness is a property of the interpreted list as a whole, not of any one printer; its state-bearing payload carries the freshness state, with its cause exactly where the state carries one — Pending and NeverInterpreted (document problems included, which have no existence independent of a freshness state); Fresh is causeless and carries the interpreted list instead. Every durable event's payload also carries the session's current turn-in-flight flag where a session is its entity (session deleted excepted — its payload stays the key alone), and a session's state-fetch response carries the same flag — the fetch side is how a joining device learns of a running turn when no event happens to be in flight.
- **Ephemeral events** — fan-out only, never buffered, never replayed, never emitted for a deleted session (deletion's observability covers ephemerals like everything else), and each carrying its session key (a stream can span sessions, so a turn signal or delta must say which session it belongs to): streamed-text deltas (each carries the *entry key* its durable text-segment entry will carry — a per-entry key, not the message-lifecycle contract's per-turn message key, since one turn can commit several text segments; the stream's first delta is marked as its head), turn-started, and turn-ended (emitted at every turn acceptance and terminal, whatever initiated the turn — send, retry, or automatic resume).
- **Sync tokens** — every durable event and every state-fetch response carries an opaque ordered token. Granted client operations, and only these: present a token back as received; order-compare tokens received on one live stream and its interleaved fetches; discard every held token when told to resync. Clients never construct, decode, or compare tokens across a resync.
- **Subscription** — a client opens the stream presenting a token (its first fetch's, at load; the stream's own last-seen, on reconnect) and receives every durable event after it. When the transport cannot honour that (the token predates what it can replay, or predates the current service run), it answers with an in-stream *resync-required* signal on a subscription that stays open and keeps delivering — never a terminated stream — and the client refetches its views over it. An idle stream carries a periodic heartbeat.
- **Event subscription seam**: both emitters expose a multi-consumer subscription delivering the events above — keyed, state-bearing, at-least-once, in commit order — and that seam is all a module-internal subscriber consumes: the token and resync vocabulary is `server`'s transport realization for remote clients only (`server` relays payloads verbatim, stamps tokens, and never synthesizes keys or payloads). A direct subscriber gets the same convergence guarantee without tokens, by composition: subscribing and then fetching current state loses nothing — an event concurrent with the fetch is delivered, in the fetched state, or both — and a subscriber (re)starting later converges the same way.

## 3. Guarantees and invariants

- **Convergence**: every connected device converges on committed state without manual refresh; a missed change is eventually applied or the device knows to refetch — a view is never silently stale.
- **At-least-once, exactly-once rendering**: delivery may duplicate but never loses; consumers must apply any durable event twice with the effect of once (the keyed, state-bearing payload is what makes that possible). A committed transcript entry renders exactly once on every device regardless of how connects, disconnects, fetches, and restarts interleave with the commit.
- **Order**: durable events for one *session* — every entry kind and session-scoped change alike — for one printer, and for the printer-knowledge singleton (successive freshness changes) are delivered in commit order within a stream; entry keys exist for deduplication, never as ordering scopes, so a turn's text segments, tool calls, tool results, and failure entries arrive in the arrival order the message-lifecycle contract's transcript honesty requires. Deltas sharing one entry key are delivered in emission order — the sink's ordering carried to the wire — so live text renders in sequence, never garbled; only cross-entry ordering is the durable stream's business.
- **Gapless composition**: fetching and subscribing compose gaplessly in either order — the load-time fetch-then-subscribe and the resync refetch-over-an-open-stream alike: an event concurrent with a fetch is in the fetched state, replayed, or both; never neither. A paginated fetch composes the same way page by page — every page-response carries a token, and an event concurrent with any page is in a fetched page, replayed, or both (the append-only orders behind paged listings put concurrent growth at the tail, where later pages or the replay absorb it).
- **Cross-restart safety**: a token from before a service restart is always answered resync-required — a resuming client is never mis-served different content under a reused token.
- **No partial streams**: a client renders a delta stream live only if it observed the stream's head; otherwise it ignores the deltas and waits for the durable entry — never a mid-sentence fragment presented as a message.
- **Turn visibility**: a running turn is visibly in progress on every connected device — joining and reconnecting devices included, via the fetched turn-in-flight state and the flag on durable payloads — and never shows as running after it ended, with any wrongness bounded by the turn's next observable activity.
- **Liveness**: the conventions' bounded-resolution rule, sharpened for this seam's persistent connections — opening a stream resolves to an open stream or a structured error in bounded time, and a dead connection becomes visibly disconnected within a bounded time even when nothing is being emitted; idle and dead are distinguishable (the heartbeat is what makes an idle stream provably alive).

The session-failure condition is fetchable: a device connecting for the first time — or reconnecting past the replay window — while the condition stands sees it in fetched state with its cause and the affected entries' keys, sufficient to localize each piece of stuck content (asserted with two entries stuck at once); a second entry joining the standing condition fires its event on a connected device — the grown key-set arriving live, never only on refetch (asserted); the clearing event and the cleared fetched state both follow when the content lands.
