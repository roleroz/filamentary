## 1. Scope

Files and images: how they enter a session, how they are identified, and how every consumer reads them back. Owner: `sessions` (store and identity). Indexer: `fileindex` (`.3mf` and gcode). Consumers: `mcp` (agent access), `server`/`ui` (routes, gallery, transcript). Covers the edges `sessions → fileindex`, `mcp → sessions`, `mcp → fileindex`, the evidence routes on `server → sessions`, and the evidence semantics of prompt assembly — what an attached ref contributes — wherever a message is assembled for the backend (the rule the message-lifecycle contract cites). The cross-seam conventions (`conventions.md`) apply to every operation here.

## 2. Identity

- Every piece of evidence's identifier — uploads and attached snapshots alike — is its kind plus a per-session, per-kind sequence — and the exposed identifier always carries the kind discriminant, so any holder can read the kind from the identifier alone and identically-numbered uploads of different kinds never collide. One identifier space serves every surface: the value the user sees in a listing, the value the agent addresses tools by, and the value the transcript's tool calls show are the *same* identifier — never translated at any boundary — so citing an upload by the identifier one surface showed always resolves on every other.
- Committed sequences are contiguous and ordered by commit: an intake that does not commit — rejected, failed, or crash-aborted — consumes no number, so every committed sequence *n* > 1 has a committed predecessor *n − 1*, and a higher number always denotes a later commit — "newest" is one notion everywhere, the highest committed sequence of the kind. Identifiers are stable for the session's life and across restarts; re-slices reusing filenames get new identifiers, and filenames never disambiguate anything.
- An `EvidenceRef` *is* the exposed identifier — one value, one space, never two representations. It names one piece of evidence *within the session it is presented in*: resolution is always session-scoped, and a value carries no cross-session meaning — presented in a different session it resolves to *that* session's evidence at the same ordinal, or to nothing (the *unknown-ref* error). Cross-session impossibility is a property of operations, not of values: no operation, whatever value it is handed, can ever reach another session's evidence, and no answer reveals whether a value means something elsewhere. A value that does not parse as a well-formed ref, or carries an unrecognized kind discriminant, is simply an unresolvable value — unknown-ref, never an unclassified failure (the agent is a model; hallucinated identifiers are ordinary inputs here). `message-lifecycle`'s invalid-evidence-ref synchronous rejection is the unknown-ref error at the send seam.
- Kinds are a closed set — the supported upload types (images, `.3mf`, gcode) and attached snapshots — each kind in exactly one of the two classes every kind-discriminated rule below partitions by: *image-class* (uploaded images and attached snapshots — derivative rules, servable to the agent as image content) and *file-class* (`.3mf` and gcode — bounded views only). A file outside the set is not a kind: it draws §3's unsupported-kind rejection.
- Unqualified addressing ("the current `.3mf`") exists for the *indexed* kinds only — `.3mf` and gcode — resolving to the newest committed upload of the kind, with `fileindex` owning that resolution; image and snapshot evidence has no newest rule and is always addressed by explicit ref.
- A file-kind ref attached to a message contributes its *handle* to the prompt: identifier, kind, and original filename (length-bounded at intake, so a handle is fixed-size) — the address the agent then uses with the bounded views — never content. An image-class ref contributes its content (in consumable form) *labelled with its identifier*, so the agent can cite the image and address follow-up tools by the same value every other surface shows.

## 3. Operations

- `sessions.upload(session, kind, original_filename, bytes) -> EvidenceRef` — kind is caller-declared, and the declaration is owned by the route: `server`'s kind-specific controls declare the kind they name (the image capture and gallery controls declare image, the project control `.3mf`, the gcode control gcode), and a file submitted through one is judged by that kind's validity rules — a PDF through the image control is an unsupported *format*, not an unsupported kind; generic surfaces (the first-message attachment picker, which accepts every kind) declare the kind from the file's type — an image-typed file of any format is declared image and judged by image validity, so a BMP draws unsupported *format*; a `.gcode` or `.3mf` extension declares its kind there with precedence over the content type — the extension names intent, and the bytes then validate against it, so a renamed PNG called `part.3mf` draws `fileindex`'s invalid-`.3mf` rejection (declaration by extension is not the identity disambiguation §2 forbids — filenames never say *which* upload, but may say *what* a new file is) — and only a file neither type nor extension covers draws the unsupported-kind rejection naming the file. `upload` never accepts the snapshot kind — declaring it draws the unsupported-kind rejection; snapshots enter only through `attach_snapshot`. Which rejection a file draws is thereby fixed by the surface, never an implementation accident. Images are validated on two distinct grounds with distinct rejection reasons — the format must be a supported one (JPEG, PNG, HEIC at minimum) and the bytes must decode — per R1's two separately-observable rejections (a readable image in an unsupported format is refused as unsupported, not as unreadable); a decodable image whose required derivative cannot be produced fails intake as a *fault-class* rejection naming the file — distinct from both validity reasons, with the same residue-free unwind — and any other system fault during intake — a failed write, an unwritable store, or a fault *inside `fileindex`* such as an unwritable index — is the same fault class, never conflated with invalidity: only judgments about the file's content are ever relayed as rejection reasons; `.3mf`/gcode validate via `fileindex.validate_and_index`, whose rejection is relayed verbatim. The printer name is never a validity input: a `.3mf` indexes successfully with a name, without one, or with one that cannot currently be read — intake rejects only structural invalidity, so a name-read fault fails no upload. Afterwards, `fileindex.printer_name(session, ref) -> Result<name | none, Error>` reads the indexed project's name for the upload's life, by explicit ref — any committed `.3mf`, so the binding contract can address the specific upload its derivation names, newest or not; a non-`.3mf` ref draws the kind error and an unresolvable ref unknown-ref, per the views' partition; a failed read (an unreadable index) is the structured read-failure, never a no-name answer, since the binding contract gives the two opposite consequences (immediate no-op versus deferral).
- `sessions.attach_snapshot(session, image, provenance) -> EvidenceRef` — the same intake guarantees as an upload; provenance (camera, capture time) originates at capture and is preserved unmodified. A snapshot that fails intake — a successfully fetched camera body that does not decode, the case the release list flags as live — is a structured capture-failed error to the requester naming the camera and the reason, distinct from the printer-state contract's fetch failure (the fetch succeeded; the body did not decode): the user path renders it, the agent path receives it as the tool's error. Capture-failed is the *validity* surface only — a system fault during the attach (derivative production, a store write) stays the fault class naming the system, never the camera, so the remedy split holds on this path too.
- `sessions.evidence_list(session)` — every piece, with identifier, kind, and its provenance, where provenance means origin metadata: a snapshot's camera and capture time, an upload's original filename and upload time — never a fresh window, since evidence is never staleness-judged (the window belongs to printer-state's live values); listed in intake commit order, append-only for the session's life, and paged with a bounded page size and an honoured-or-refused continuation — refusal arising only at service-run boundaries, never silently re-resolved, with the append-only order keeping a continuation valid across concurrent intake (R5's iterate loop grows sessions without limit, so "one row per attachment" is proportionality, not a bound).
- `sessions.evidence_bytes(session, ref, variant: Display | Original)` — session-scoped like every read on this seam, since the ref alone names nothing without one (§2). Display (the default every current consumer uses) serves a form the requester can consume: for images, a bounded derivative wherever the original is browser- or model-unconsumable (HEIC) or exceeds the size bound, else the original — a derivative differs from its original only in encoding and scale, never in content (no cropping, no redaction, aspect and orientation preserved), so the evidence stays judgeable; for file kinds, the original bytes with their mime. Original always serves the stored bytes. Display's failure surface is the *original's*: a derivative that is missing or unreadable over a readable original is reproduced from it rather than failing; a reproduction that itself fails draws the fault-class error naming the file — the read-time twin of the intake derivative fault, distinct from read-failure, with the original still retrievable via Original — and the read-failure error means the stored bytes themselves cannot serve. Provenance rides the response envelope alongside the bytes on both variants — never dependent on metadata embedded in the served bytes surviving re-encoding. An unknown ref in a valid session is a structured unknown-ref error; a *known* ref whose stored bytes cannot be read — vanished or unreadable — is a distinct structured read-failure error naming the path and operation (R10: this is a failure a user can trigger from the gallery, and it must never look like an unknown ref or hang), and `evidence_list` fails the same structured way when the listing itself cannot be served. `evidence_bytes` itself is a trusted internal seam serving any module any kind — the never-whole-file restriction lives at the *agent-facing surface*: refs of every kind legitimately circulate to the agent via evidence listings, so whatever operations that surface exposes must refuse a file-kind read with a structured kind error (a runtime refusal, since the ref is addressable) while serving image-kind refs as image content; the kind error takes precedence over resolution — it is decided on the ref's kind discriminant alone, so a wrong-kind ref draws it whether or not its ordinal resolves; only the bounded views reach file-kind content.
- `fileindex` views (settings, settings diff, gcode regions and search, mesh measurements and rendered views, thumbnails, summaries) — addressed within a session, like every read on this seam: every response bounded; a truncated response says so and how to continue; a continuation is honoured exactly or refused explicitly, never silently re-resolved — the general rule mutable-content seams share, each adding its own refusal conditions (the printer-state contract's log views refuse on rotation); *here*, since committed content is immutable and unqualified views are pinned, refusal arises only at service-run boundaries (a restart or an index rebuild), never from content change. Unqualified addressing resolves once, when the view starts, and continuations stay pinned to that upload — a newer upload committing mid-iteration never mixes pages. An unqualified query in a session with no committed upload of the kind draws a distinct structured no-upload answer — an answer, not a failure, and the observable behind R5's ask-for-the-project behaviour; an *explicit* ref that resolves to nothing is always unknown-ref, never the no-upload answer, which belongs to unqualified queries alone. A view addressed at a ref of the wrong kind draws a structured kind error; an index that cannot be read draws a structured read-failure error naming the path and operation. `fileindex.remove_session(session)` drops a session's index whole; it is idempotent — re-invocation, including for a session that never had an indexed upload, completes cleanly, which the deletion re-drive depends on.

## 4. Guarantees and invariants

- **All-or-nothing intake**: a rejected or failed upload (first-message attachments included) leaves no observable residue — no row, no file, no derivative, no index entry, no event, no sequence number consumed — and the rejection names the file and the reason. Validation happens before anything becomes visible.
- **Cross-module intake atomicity**: an accepted upload commits whole across `sessions` and `fileindex` — after a crash at any point, a restart observes either the prior state or the completed upload, never an index entry or evidence row the other side lacks. A fault during a rejection's unwind re-drives per the conventions until residue-free, and the half-unwound intermediate is unobservable meanwhile: an index entry whose evidence row is absent is never served and never counts as newest.
- **Session existence**: per the conventions, with one seam-specific sharpening — the unknown-session error is never conflated with unknown-ref, which is reserved for a live session's unresolvable value. `fileindex` itself is *session-blind*: it answers content questions only, and session existence is resolved by its callers before it is consulted — `mcp` resolves the session at `sessions` while handling a tool call, and `server`'s routes resolve through `sessions` — so the unknown-session answer is always the caller's, and the deletion cascade needs no `fileindex`-side session knowledge, only `remove_session`'s idempotent drop.
- **Bounded prompts, per item and per send**: a whole `.3mf` or gcode file never enters a model prompt; file kinds are reachable by the agent only through `fileindex`'s bounded views; image evidence reaches the model only in a consumable, size-bounded form; and one send's ref contributions — images and file handles alike — are capped by *count*, each item already size-bounded (Display for images, the fixed-size handle for files), so the cap bounds the whole send's contribution — and a send exceeding it draws a synchronous rejection at the send site naming the cap and the excess (the message-lifecycle contract's line), never a single send's attachments failing as an opaque backend error. Conversation growth across many turns — the agent's own bounded reads included, however many a turn spends — is the backend's context to manage; its overflow surfaces as a classified backend failure per the message-lifecycle contract, not through this cap.
- **Consumable forms**: browsers and models are only ever handed formats they can display or read; the original bytes remain retrievable explicitly.
- **Provenance end-to-end**: a snapshot's camera and capture time survive from capture through storage to every display and read-back.
- **Revocation**: deleting a session removes its files, its index, and every access path (the agent's included) — under any crash/retry interleaving, completed by re-drive, never half-done; a cascade step failing while the service runs is re-attempted in bounded time per the conventions' re-drive rule, never left to the next restart.
- **Gating**: agent-initiated snapshots are print-gated (per the printer-state contract); user snapshots are not; both attach as ordinary evidence through this contract.
- **External facts carried for release verification** (per the harvest): a *real phone-captured* HEIC (HEVC-encoded HEIF) must pass intake before first release — fixture HEICs are produced by the validating stack itself, so the mocked suites cannot prove it; an image served through the agent-facing surface must be confirmed to reach the live model as vision input — the scripted suites consume this seam directly and can never prove what the model sees; and a *real webcam endpoint's* captured body must pass intake — what real crowsnest returns is decided at this seam's validator, and the mocked suites cannot prove it accepts it.

Scenarios:

1. Identity: kind-discriminated identifiers, no cross-kind collision, one identifier space end to end — the value from a listing resolves identically through the agent's tools and appears verbatim in the transcript's tool calls (asserted across all three surfaces); re-slice filename reuse yields distinct identifiers; identifiers stable across restart, with both byte variants and their provenance serving identically after one (asserted).
2. Intake reason partition, every reason asserted distinct and residue-free, at upload and as a first-message attachment, user and agent snapshot paths alike: accepted JPEG/PNG/HEIC (with derivative); oversized image (bounded derivative, original retrievable); undecodable bytes; readable image in an unsupported format (refused as unsupported, not unreadable); unsupported kind (a `.stl` or PDF, reason-naming the file); invalid `.3mf`/gcode with the `fileindex` reason relayed verbatim; the derivative fault-class and store fault-class rejections distinct from every validity reason (the remedies differ: a fault to report, not a photo to convert); every rejection consumes no sequence number — the next successful intake is contiguous (asserted per reason); the same PDF asserted drawing unsupported-format through the image control and unsupported-kind through the generic picker; a fetched camera body that fails decode draws the capture-failed error naming the camera — distinct from the fetch failure — on the user and agent paths alike (asserted).
3. Intake concurrency and crash: the cross-module crash window in both interleavings — after restart, the prior state or the completed upload, never an orphaned row or index entry; a crash-aborted intake burns no number — the sequence is contiguous after restart with a subsequent successful intake (asserted); two concurrent intakes where one fails leave the survivor committed contiguously; two concurrent successes commit distinct, contiguous identifiers — no duplicate, no gap (asserted under injected races, per R1's simultaneous multi-device use).
4. The agent-facing surface: no operation returns a `.3mf` or gcode whole — the whole-file request draws the kind error while the bounded views serve (R5's never-whole-file criterion); an oversized or HEIC image arrives as the bounded Display form, never Original (asserted on bytes and mime); an image-class ref reaches the prompt labelled with its identifier, a file-kind ref as exactly its handle — identifier, kind, original filename — with no content (asserted on the assembled prompt at the backend seam); a send exceeding the per-message attachment bound — images and file handles alike — draws its synchronous rejection at the send site (asserted).
5. Cross-session isolation, asserted per operation — bytes and views alike: a value carried over from another session resolves session-locally, to this session's evidence at that ordinal or to unknown-ref, never to the other session's content.
6. Deletion: full revocation including agent access, asserted after a crash mid-cascade and re-drive; at the crash point every `sessions` operation already answers unknown-session — no listing ever shows evidence whose bytes are gone (asserted); an upload racing the deletion commit ends with nothing of the session remaining, for both interleavings (asserted under an injected race).
7. Provenance: the capture-time values survive to `evidence_list` and both byte variants, on the user and agent paths alike, riding the response envelope.
8. Display fidelity: the derivative preserves the full frame — dimensions scaled, aspect and content intact (asserted).
9. Release items (live suite): a real phone-captured HEIC passes intake; an agent-served image reaches the live model as vision input; a real webcam endpoint's captured body passes intake.
