## 1. Scope

A user message's whole life: submission, the backend turn, the transcript record, failure, retry, automatic resume, and recovery after crashes — plus session teardown at the backend. Participants: `server` (routes), `sessions` (transcript owner and domain instructions), `agent` (backend boundary), `mcp` (per-session endpoint provisioning), and `printer` (the one other backend caller, via `interpret_document`). Covers the edges `server → sessions`, `sessions → agent`, `agent → sessions` (event sink), `agent → mcp`, and `printer → agent` (interpretation). The cross-seam conventions (`conventions.md`) apply to every operation here.

## 2. Operations

- `sessions.create_with_first_message(text?, attachment?) -> {session, derived_name}` — creating a session *is* sending its first message; the local name derivation needs no model. Creation atomically includes the session's endpoint provisioning (`mcp.endpoint_for`): a provisioning fault rejects the creation whole. At most one attachment rides the create (further evidence follows in-session, where `send` takes any number of refs); an invalid attachment rejects the whole creation synchronously — no session exists afterwards, per the evidence contract's residue-free intake.
- `sessions.send(session, text?, evidence_refs)` — one call carries the message and drives the turn; there is no separate append step. Refs may be of every kind; image refs are model-visible in the prompt, file refs are named context (see the evidence contract).
- `sessions.retry(session)` — re-offers the failed message; a pure delegation to `agent.retry`.
- `agent.send(session, key, content, instructions)` / `agent.retry(session)` — `key` is the caller-minted message key correlating the turn — its user-message entry, its sink events, and crash recovery; the entries a turn commits each carry their own per-entry key, minted by the transcript owner per the events contract. `agent` persists what a restart needs to re-send and to restore the user-message entry (text and refs) without `sessions` re-assembling, and exposes it: `agent.pending_message(session) -> Result<{key, content} | None, Error>` is the read recovery restores from.
- `agent.backend_state(session) -> Result<Exists | None, Error>` — a definite answer to whether anything of the session *currently* stands at the backend; a torn-down session answers `None` (teardown is what makes destruction safe), and the error arm is mandatory, since callers destroy state only on a definite `None`.
- `agent.teardown(session) -> Result<(), Error>` — the error arm structured and retryable, so the deletion cascade can surface standing trouble rather than silently re-driving; removes every backend artifact (mapping, pending message, scheduled resume, and the session's MCP endpoint via `mcp.revoke`); idempotent and retryable, callable during the session's own in-flight turn.
- `agent.interpret_document(text) -> Result<Printers, Error>` — one-shot, sessionless, no MCP endpoint; subject to the same bounded-resolution guarantee as any turn. Its failures classify per §3 with one exclusion: never `interrupted` — nothing persisted survives to be interrupted, a service restart simply abandons the call (the printer-state contract's crash-cost rule covers the redundant attempt).
- `mcp.endpoint_for(session) -> Result<endpoint, Error>` (idempotent) / `mcp.revoke(session) -> Result<(), Error>` — the endpoint is a per-session URL carrying an unguessable credential scoping every tool call to its session; *that credential* is what `revoke` invalidates: every subsequent use of the endpoint is rejected. Both error arms are structured and retryable; a provisioning fault surfaces per the synchronous/asynchronous line like any other failure — known before acceptance, it rejects the send or creation synchronously; discovered after, it classifies as an internal fault. Revoke is idempotent, including for a session never provisioned; a partially completed revoke completes on re-invocation. The endpoint is stable for the session's backend life across service restarts — a re-provisioning call after a restart returns the same endpoint, since a resumed conversation may still hold it; only `revoke` retires it.
- Composition guarantees (the root's obligations, however wired): no event delivery, recovery action, or backend call can run before everything it reaches is bound — `agent` can always reach its endpoint provider and its sink when anything needs them, and `sessions`' startup recovery scans run only after all cross-module reach exists; a scans failure leaves the service running, with `sessions` owning the re-drive of incomplete recovery.
- **Sink events** (`agent → sessions`, in order): `Text(key, chunk)`, `ToolCall`, `ToolResult` (structured payload relayed verbatim, never flattened), `TurnEnd` (successful terminal only), `ResumeFired` (an automatic resume is starting), `Failure(error)` (failed terminal; carries the classification below). Backend update kinds outside this vocabulary are dropped and logged, never leaked into the transcript.

## 3. Failure classification and the synchronous/asynchronous line

Every failure carries exactly one classification, each with a user-renderable cause and its recovery path: **auth** (naming the source in play — env token or `~/.claude` — and that source's remedy), **no-credentials** (both remedies), **usage-limit** (with the reset time when one is parseable), **outage**, **protocol**, **timeout**, **backend-unavailable** (the backend's own process or connection died during an accepted turn, the service still running — discovered mid-turn), **interrupted** (Filamentary's own restart or a recovery action cut the turn short — the backend itself may be fine), **internal fault**. All are retryable. Interpretation adds one classification of its own: **malformed-output** — the reply could not be parsed as the expected result; retryable like the rest, and a fault of the attempt rather than of the document or the backend's availability, which is how its one consumer files it (the printer-state contract classes it with the backend-class retry causes). The distinction from the synchronous *backend-restarting* rejection is detection timing: unavailability *known at send time* rejects synchronously before acceptance; unavailability *discovered after* acceptance classifies asynchronously as backend-unavailable.

The line: a rejection *before* the backend accepts the message is **synchronous** — an error to the caller's action site, with no transcript entry, no event, and no persisted state anywhere; the caller's standing content is untouched — a send's composer text intact (the user re-sends), a retry's failed message and transcript exactly as they were. The synchronous set: turn already in flight (busy), backend restarting (its unavailability known at send time), an evidence ref that does not resolve in the session (the evidence contract's unknown-ref), an attached ref whose content cannot be served at prompt assembly (the evidence contract's read-failure or derivative fault-class, relayed with the ref and cause — never a prompt with the attachment silently omitted), a send exceeding the per-message attachment bound (the evidence contract's bounded-prompts rule at the send site), an invalid first-message attachment (rejecting the creation whole), an empty message (no text and no attachment or ref — rejected whether creating or sending; there is nothing to send), nothing to retry (a `retry` with no failed message standing — one racing a success or an automatic resume draws this rejection, never a duplicate send), unknown session, and a pre-acceptance storage or endpoint-provisioning rejection. Every failure *after* acceptance is **asynchronous** — a transcript failure entry with a working retry. Consumers can rely on the line: a message rendered as sent was accepted.

## 4. Guarantees and invariants

- **Never silently lost**: after any single crash or restart at any point, an accepted message is delivered, or visibly failed with a working retry — never invisible and unretryable.
- **Never silently duplicated**: no path re-sends an accepted message to the backend without an explicit user action or a visible note; accepted double-fault degradations are visible and bounded, never silent.
- **Transcript honesty**: the transcript never shows a reply or failure answering a message it does not show; user text, streamed output, tool calls and results, and failures appear in arrival order; a failed turn's already-streamed text is preserved ahead of its failure entry.
- **Live persistence failure**: accepted content whose transcript write fails while the service keeps running is never silently dropped and never an error inviting a re-send of a message the backend has — persistent failure becomes a visible *condition* on the session, readable in fetched state and announced through the events contract's session-failure event, standing until the content lands (a crash while the condition stands is the accepted bounded loss: committed entries are what durability covers, and the condition made the trouble visible first). The condition aggregates and never gates: it stands while *any* accepted content is unpersisted, carrying the key of every stuck entry, and clears only when all land; a standing condition blocks no send or retry — acceptance and the condition are orthogonal, and further stuck content joins the condition rather than overwriting its visibility. The user-message entry is never part of the accepted bounded loss: `agent.pending_message` holds it durably until its transcript write lands, so a crash while it is stuck restores it after restart — the loss class covers only content with no other durable home — the backend-produced entries of the turn (streamed text, tool calls, tool results), system notes, and failure entries; the user-message entry alone has that backstop. A confirmed deletion supersedes a standing condition: it proceeds, discarding the stuck content with everything else — R4's confirmation covers exactly that loss — with the session-deleted event as the terminal and no clearing event. And a turn's failed state and retriability live in `agent`, decoupled from the transcript write: `retry` works even while the turn's own failure entry is stuck in a standing condition — the entry lands later, and the retry never blocks on it. Within one turn, commit order respects causality: the turn's entries never commit ahead of its user-message entry — content produced while that entry is stuck joins the condition behind it, so commit-order delivery can never render a reply above the message it answers.
- **Destruction on certainty only**: recovery destroys a session or message only on definite knowledge (`backend_state` = `None` and nothing locally committed); uncertainty — including an erroring query — always fails toward preservation; the same holds for `pending_message`: its error preserves, and restoration is re-attempted, never skipped.
- **One turn per session**: a concurrent send or retry is rejected synchronously and harms the in-flight turn in no way.
- **Automatic resume**: a usage-limit failure with a known reset time resumes by itself at that time — surviving restarts, firing late if the time passed while down, announced via `ResumeFired`, and recorded in the transcript. A resume never fires into a running turn and never re-sends a message that succeeded; any user send or retry supersedes it. Without a parseable reset time, the failure says so and manual retry stands.
- **Credential recovery**: fixing credentials makes the next attempt succeed with no service restart — replacing the environment token excepted, which requires one (R2.2); a fresh install's first message fails visibly and recoverably with the session created, named, and its message kept. With both credential sources present the environment token is the one used, and its rejection never falls back to `~/.claude` silently — the failure names the token as the source (R2.2).
- **Bounded resolution, sharpened for turns**: the conventions' bounded-resolution rule covers every backend interaction, interpretation included; the seam-specific half is that a turn which is still streaming is never killed for taking long — the bound applies to silence, not to progress.
- **Recovery isolation**: recovering one session's backend trouble never costs another session more than a visible, retryable interruption; a per-call content problem — interpretation output that fails to parse — costs nothing beyond its own call, surfacing as `interpret_document`'s structured malformed-output error to its caller and touching no session, no backend reconnect, and no other call.
- **Deletion permanence**: after teardown — under any crash/retry interleaving — nothing of the session can resurrect: no pending message, no scheduled resume, no backend mapping, no tool access; late events for a deleted session are dropped.

5. 6. 8.
