## 1. Scope

Everything the system knows about printers and how consumers reach it: the interpreted printer list and its freshness, per-printer reachability, telemetry and Klipper log/config views, webcams and snapshots. Owner: `printer`. Consumers: `sessions` (binding match, freshness events), `mcp` (telemetry/log/snapshot tools), `server`/`ui` (printers screen, degraded bar, user snapshots). Covers the edges `server → printer`, `sessions → printer`, and `mcp → printer`. The cross-seam conventions (`conventions.md`) apply to every operation here.

## 2. The list and its freshness

- `printers() -> Result<{list, freshness}, Error>` — never blocks on the model, fresh install included. Each entry: canonical name, aliases, optional Moonraker URL (absent = evidence-only) — exactly what the document conveys per R3, nothing more; telemetry capability *is* the URL's presence, and webcam capability is discovered live, never carried in the entry. The error arm is a *call-time* failure to serve any answer at all — the retained knowledge cannot be read right now — and is always transient and retryable; a fault that still leaves a servable answer (a failed retention write, a failed attempt) is never an Error but a freshness cause, so the boundary is: Error when nothing can be served, freshness-with-cause when something can. Consumers treat Error as transient unknowability (the binding contract defers new conclusions on it while standing states keep serving; the UI renders a transient failure, not a printer state).
- `freshness` is one of: **Fresh** — the list matches the document's current content; **Pending(cause)** — a previously interpreted list is serving, but the current content is not successfully interpreted; **NeverInterpreted(cause)** — no list has ever existed. Both carry a cause from one taxonomy: an interpretation in flight; a backend failure (by classification); a document *content* problem on a readable document (no identifiable printers, duplicate names) — naming the path; the document missing or unreadable — naming the path (spec R3 requires the path and the problem user-visible in both freshness states); a fault of the retention store itself (never misattributed to the backend); or the location option being unset — reachable in both states, since a retained list survives a later config unsetting, and this cause names the option rather than a path.
- **Interpretation obligations** (what, not how): an edited document is re-interpreted without a restart; a failed attempt is re-attempted when its cause class can have changed — backend-class causes (every failure classification, *and* interpretation output that failed to parse, which is a fault of the attempt rather than the document: the model simply tries again) on next use, a retention-store fault likewise on next use (transient like the backend class), document-class problems only once the document changes, and the location-unset cause once the option is set — setting it is the input change that re-triggers, there being no document to edit; content whose successful interpretation is already retained is never re-interpreted (edit-then-revert costs nothing); concurrent loads never run concurrent interpretations; a failed or crash-abandoned attempt never corrupts the retained list (all-or-nothing); a crash mid-interpretation costs at most one redundant model call after restart; an interpretation result is committed only for the document content it interpreted — a result landing after a further edit is never marked Fresh against the newer content (the next interpretation covers it).
- Duplicate names in an interpretation are a document problem: reported, with the previous retained list left in force.

## 3. Reachability and telemetry

- `reachability(printer)` returns exactly one of: **Reachable** (last failure retained for diagnosis without affecting the verdict), **Unreachable(cause)** — the cause from a small taxonomy a consumer renders per R10: connection failure, timeout, or protocol failure (an error status or a malformed response) — **Unknown** (no observation yet this run), **NoTelemetry** (evidence-only — standing exactly as long as the current list's entry carries no URL, with no Moonraker or webcam call ever attempted meanwhile; a later Fresh list granting the printer a URL lifts it). Unknown is neutral, not degraded: consumers show no degraded state and disable nothing for it, and any operation attempted while Unknown simply proceeds — its outcome is the first observation. Reachability and the retained last failure are per-run: a restart resets every URL-bearing printer to Unknown — NoTelemetry, derived from the list entry itself, stands unchanged across restarts — a Fresh list changing a printer's URL in place likewise resets it to Unknown (the old endpoint's diagnosis never describes the new one), an observation landing after a Fresh list removed or changed its printer's URL is discarded — NoTelemetry or the reset stands, and a stale in-flight call never overwrites either — a printer whose name leaves the list and later reappears starts at Unknown with nothing pre-removal resurfacing, and entering NoTelemetry clears the retained last failure — the diagnostic context it belonged to is gone, so a later URL grant starts clean. Any telemetry, log, config, or webcam operation addressed at an evidence-only printer — `snapshot()` included, refused before any discovery is attempted — draws a structured no-telemetry error with no Moonraker call: the operation-level answer behind the NoTelemetry verdict. The reachability verdict is `printer`'s own — consumers never derive it. Observation-driven: outcomes of actual Moonraker calls decide it — telemetry, log, config, *and webcam discovery* alike, since discovery is a Moonraker call like any other — with no background polling; the exclusions are exactly two — the snapshot *fetch* (it goes to the camera host, not Moonraker; its failure is transient per R7 and never flips reachability) and the NoTelemetry verdict, which derives from the list entry and never from observation.
- Telemetry (`status`, `temperatures`, `position`), and the log/config views below, each return a result or a structured, retryable error carrying the same cause taxonomy as `Unreachable` (connection failure, timeout, protocol failure) — the failing call's outcome *is* the observation that flips reachability, and its caller always receives something renderable per R10. All of `printer`'s I/O — Moonraker reads, webcam discovery, snapshot fetches, and its own retention-store reads behind `printers()` — resolves to content or a structured error in bounded time; nothing hangs, spins, or waits silently (the cross-cutting rule carried for this contract's own operations). Read-only by construction — no state-changing Moonraker call exists in the client's surface. Every result carries provenance: source and the absolute capture timestamp, with the expected-fresh window on the values that have one — the window belongs to live telemetry values, and config and log views, being non-live content, carry none; consumers judge staleness at view time against the timestamp (so a value's staleness can change on screen), and the judgment applies only to fresh-window-bearing values (the settled brand decision).
- Klipper *log*: bounded, continuable views (tail, range, search) — never whole, and never content from before Klipper's last restart; when that boundary cannot be found, views serve what exists and say the boundary is unknown; continuations follow the evidence contract's rule — honoured exactly or refused explicitly, valid across pure growth of the live log, refused on rotation. Klipper *config*: a fetched-fresh, non-temporal read served by section, with the section names enumerated by a listing operation (`config_sections(printer)` — discovery like every other on this seam); each section bounded and continuable — a truncated section says so and continues, honoured exactly or refused explicitly, never silently incomplete, with the refusal's one trigger being the section's content changing between pages (config is fetched fresh, so a continuation is never spliced across an edit) — and never whole; a query naming a section outside the listed set draws a structured unknown-section error — the restart boundary and growth/rotation rules are log concepts and do not apply to it.
- Any per-printer operation given a name outside the current list — reachable at any moment, since the list changes asynchronously — returns a distinct unknown-printer error, never undefined behaviour.

## 4. Webcams and snapshots

- `webcams(printer)` — discovery through the printer's Moonraker, with the two empty-looking outcomes kept distinct: an *answered* empty list means the capability is absent (R7: no snapshot action offered, everything else normal), while a discovery failure (Moonraker unreachable) is a structured error (R7: the control disabled with the reason shown) — a consumer can always tell absent from unknowable.
- **The session's camera choice** — stored by `sessions` (session state, settable whenever a discovery has offered cameras — in practice the bound family, since the webcam routes are binding-gated per the binding contract — readable in any binding state, surviving every later state once set, and shared across a session's devices; its changes ride `sessions`' camera-choice-changed durable event) and carried on each capture request; *this contract owns its capture-time semantics*. The choice names a camera *of a specific printer*, and its scope — that printer's canonical name and telemetry URL — is recorded at set time from the discovery that offered the camera, not from the binding: the scope needs no binding to be recorded, though the offering routes themselves are binding-gated per the binding contract. Validation happens only at capture (a choice may name a camera discovery can't currently see; the capture is where truth is checked): a capture whose target printer differs from the recorded scope — a different canonical name, or the same name re-pointed at a different URL — is refused with a structured out-of-scope error naming the printer the choice was made on, never a capture from any camera; so a stale choice can never silently select another printer's camera, however the list changed, while missing-and-back and ambiguity round trips to the same printer leave the choice standing.
- `snapshot(printer, camera_choice?, requester: User | Agent)` — the session's stored choice (carried by the caller) or the first discovered camera; with no choice and an answered-empty discovery, the capture is refused with a structured no-camera error (capability absent at this moment), and a discovery failure is its structured unreachable error; a supplied choice naming a camera no longer among the discovered ones is refused with a structured unknown-camera error naming it — never a silent capture from a different camera, which would falsify the provenance the user chose by; a discovery *failure* at capture time is the structured unreachable error whether or not a choice was supplied — a choice cannot be validated against an unanswered discovery, and unknown-camera is never claimed on one; the resolved camera and capture time form the snapshot's provenance, born here. `Agent` requests are refused with a structured reason unless Moonraker reports an active print (printing or paused), and the refusal names which case: no active print (Moonraker answered, idle) or print state undeterminable — the latter carrying the underlying cause (connection, timeout, protocol) in the refusal payload itself, per R10, never requiring a separate `reachability()` read — distinct reasons, since R7 sends the user different asks; `User` requests are gated only by reachability. Transient fetch failures are structured and retryable, carrying the same cause taxonomy as Moonraker calls — connection failure, timeout, protocol failure — against the camera host, and never attach anything downstream.
- Real-deployment resolution of camera URLs (commonly relative, served off the printer host's frontend) is an external fact on the harvest's release-verification list; the contract's obligation is only that discovery-reported cameras are fetchable on the common real setups, verified there.

## 5. Events

Freshness and reachability changes are emitted to a multi-consumer subscription — `server` subscribes for fan-out of both kinds; `sessions` subscribes to freshness only, for the binding contract's re-derivation on freshness changes, and receives no reachability events — keyed and state-bearing per the events contract — a freshness event carries the new state *with its cause* (document problems ride here; they have no independent event), and a Fresh event carries the new list.
