## 1. Purpose

Filamentary's MCP toolset offered to the agent, per the architecture: thin delegation to `fileindex`, `printer`, and `sessions`, enforcing only its three scoping duties (per-session endpoints, the binding gate on printer-facing tools, the file-kind restriction on evidence read-back). The seam behaviour lives in the contracts; this document covers the endpoint mechanics, the tool catalog, and the per-call pipeline.

## 2. Internals

- **Endpoint host** — a streamable-HTTP MCP server mounted on the service's HTTP listener; each session's endpoint is a path carrying an unguessable random credential token. The endpoint table (session, token, revoked flag) is persisted; the token is the endpoint's stable identity, and `endpoint_for` composes the URL at call time from the persisted credentialed path and the listener's current configured address — identical across restarts under an unchanged config, and correct by construction after a port change, when the old address serves nothing anyway (the contract's same-endpoint-after-restart rule is about the credentialed path staying live, which the table guarantees). `revoke` flips the flag — the row stays as a tombstone, so a rejected revoked token's log line can still name its session — and every request first resolves the token against the table: a revoked or absent row is the outright rejection the credential-invalidation obligation asserts. `endpoint_for` and `revoke` follow the message-lifecycle contract's context rules exactly — the no-record call provisions (the creation context; the caller invariant is the contract's), a revoked record draws unknown-session, a live-record re-read confirms existence before answering (`sessions.resolve` realizes the confirmation: Absent draws unknown-session, a fault the retryable fault class), `revoke` always leaves the revoked record behind, and endpoint-record writes serialize per session with the revoked record never overwritten live: defined there, realized here, nothing invented. Token generation draws from an injected randomness source.
- **Tool catalog** — one declaration per tool: name, JSON schema, target module call, and flags (printer-facing → binding-gated; evidence read → image-only). Tools: settings lookup/section/full/diff, gcode window/layer/feature/search, mesh measurements and rendered views, thumbnails, upload summary, evidence list, evidence image read, snapshot request, telemetry (status, temperatures, position), log views, and config section list/read — all printer-facing tools address the session's bound printer through the binding gate; there is no printer-listing tool (an unbound session's agent is told to ask the user, per the binding contract). Every tool fronting a *continuable* view — the full settings profile, the diff, the gcode windows, per-layer and per-feature extractions, and search, the log views, the config section *reads* (the section listing has no continuation), and the evidence list — carries its continuation parameter in the declared schema and the truncation marker in its result shape, and a refused continuation relays as the owning contract's distinct refusal answer — the agent can always page past a first page or learn explicitly that it cannot; the whole-result views (thumbnails, rendered mesh views, per-upload summaries, mesh measurements) are single answers with no continuation semantics, deliberately outside the family. Result schemas carry *every* component the owning contract defines on the view — provenance on log and config reads, the log views' boundary-unknown indication, truncation markers — a declared schema never silently drops what the contract serves. The `.3mf`/gcode view tools take an optional upload ref (the evidence contract's exposed identifier); where a tool's view spans both file kinds (settings, summaries, thumbnails), an absent ref requires a `kind` argument — the unqualified form addresses the newest upload *of that kind*, there being no kindless newest — while the single-kind tools (gcode windows and search, mesh views) need none; the schemas enforce the requirement, which is what makes R5's ref-addressed queries and the no-upload answer both reachable for either kind. The settings-diff tool is the one two-operand view: it takes exactly two upload refs (base and target — `fileindex`'s diff-between-two-uploads view), with no unqualified form. Same-kind-ness, and agreement between a supplied ref and an explicit `kind` argument, live in the values, not the schema: a diff whose refs carry differing kinds, or a `kind` argument disagreeing with a supplied ref, draws the structured validity rejection naming the mismatch — a runtime check in the pipeline's validation step, since JSON schemas cannot express it. The catalog is data; adding a tool never changes the pipeline.
- **Per-call pipeline** — a fixed order, each step's answer preempting everything after it: (1) resolve token → session (the credential rejection); (2) the catalog check — an unknown tool name is not an operation, so no session semantics attach to it; (3) resolve the session at `sessions` (the caller-owned session-existence step the evidence contract's session-blind rule requires — a real operation on a deleted session draws unknown-session whatever its arguments, per the conventions, so this precedes schema validation); (4) schema validation of the arguments; (5) for binding-gated tools, read `binding()` and map non-delegating states to the binding contract's structured errors (its consumer table's `mcp` column); (6) apply the kind restriction on evidence reads — a *denylist over recognized kinds*: the recognized file kinds (project, gcode) draw the kind refusal, while a value that does not parse as a well-formed ref or carries an unrecognized discriminant draws unknown-ref per the evidence contract, never the kind error (parsing precedes the restriction); delegate; relay the result or the module's structured error verbatim into the MCP tool result — cause and remedy intact, per R10. A call naming a tool outside the catalog, or arguments failing the declared JSON schema, draws a structured validity rejection naming the tool (or the schema mismatch) — the agent hallucinating a tool or an argument shape is an ordinary input here, answered per R10, never a transport-level failure. Token resolution stays first regardless: a revoked or unknown token draws the credential rejection whatever the call names — the invalidation guarantee outranks every other answer.
- **Snapshot flow** — the snapshot tool takes an optional camera parameter (R7: the agent may request a specific camera or the default); it calls `printer.snapshot` with `Agent` as requester and one of three camera shapes, never conflated: the session's stored choice passed intact as the scope-bearing choice (keeping the out-of-scope refusal reachable); the agent-named camera as the bare per-call identifier, exactly where the agent named one; or *no camera at all*, when the agent named none and `camera_choice_read` answers `None` — the call `printer` resolves to the first discovered camera or the no-camera refusal, that refusal's one reachable path. `printer` validates every shape at capture; `mcp` validates nothing camera-shaped itself. Every refusal in printer-state's partition relays verbatim and distinct: no-telemetry (an evidence-only printer, refused before any discovery), no-camera, unknown-camera (stored-stale and agent-named alike), out-of-scope (a stored choice after a re-bind), the discovery-failure unreachable error, the two agent-gating reasons (no active print versus print state undeterminable — R7 sends the user different asks), and unknown-printer (a verbatim-bound name outside the list). On success it hands the capture to `sessions.attach_snapshot`, returning the new reference (the architecture's agent snapshot path). There is no camera-listing tool, for the same reason there is no printer-listing tool: a specific camera identifier reaches the agent from the user, who sees the discovered set in the UI's picker; the stored choice covers the default, and a wrong identifier draws printer-state's unknown-camera refusal.
- **Statelessness** — no state besides the endpoint table; no transcript writes; no caching of module answers.

## 3. Interface

Public: `endpoint_for` / `revoke` (message-lifecycle contract) and the MCP wire surface itself. Consumed operations: the contract-defined ones per their contracts — `binding()` (binding contract), `evidence_list`/`evidence_bytes` and `attach_snapshot` (evidence contract), `fileindex`'s views (evidence contract — `printer_name` is `sessions`' binding-derivation read, never consumed here), `printer`'s operations (printer-state contract) — plus the session-store contract's `resolve(session)` for the per-request pipeline's existence step and its camera-choice read for the snapshot flow: defined there, cited here, never invented here. Module-private: the catalog declaration type, the pipeline, and the listener-address value `endpoint_for`'s URL composition uses (handed at wiring by the composition root; the port option applies only at the next start, so the value is fixed for the process's life and a config change reaches it through the restart's re-wiring — no per-call read, no reachable runtime failure), all directly testable.

## 4. Error handling and failure visibility

Every failure a delegate returns is relayed as a structured MCP tool error with the original cause — never re-worded, never collapsed. Pipeline-original errors: the credential rejection (revoked or unknown token, logged with the token's session where known), the binding-gate errors, the kind refusal, and unknown-session from the resolution step. A delegate fault (as opposed to a delegate's validity answer) is additionally logged with the tool name and session; the same holds for `mcp`'s own endpoint-store faults — every fault-class error this module originates logs with the operation name (the tool name for tool calls, `endpoint_for`/`revoke` otherwise) and the session where known — while validity answers (the credential rejection aside, which logs per its own rule) log nothing. Pipeline-original validity rejections also cover the unknown-tool and schema-mismatch answers above. The tool result still carries the fault structurally, so the transcript shows the agent exactly what failed.

## 5. Test plan

Contract tests (`test_contract_*`), unit level, with faked `sessions`/`fileindex`/`printer` and a stateful endpoint-table fake:

1. Endpoint lifecycle: `endpoint_for` idempotent (same credentialed path twice), stable across a simulated restart under an unchanged config, and serving the re-wired address after a restart whose config changed the port (same path, new address — asserted); a call with no row provisions (the creation context — asserted as the contract's atomic-creation sanction); a revoked row draws unknown-session (provisioning never un-revokes); a re-read of a live row confirms existence — resolve Absent draws unknown-session (the deleted-while-down window, asserted), a resolve fault the retryable fault-class error, never a live endpoint (asserted); `revoke` idempotent including never-provisioned, where it writes the tombstone — a later `endpoint_for` on that session drawing unknown-session (asserted); and a revoked token's request rejected outright before any delegate call.
2. Token unguessability: tokens come from the injected randomness source at full width; two sessions never share one.
3. The binding gate and printer-verdict mapping: each non-delegating binding state maps to exactly the contract table's error for every printer-facing tool; delegating states pass through and compose with printer-state's closed verdicts — NoTelemetry and unknown-printer each relayed distinct on every printer-facing tool, the snapshot tool included, and the config tool's unknown-section answer relayed distinct from every config fault — never coerced into a fault; non-printer tools never read the binding.
4. Kind restriction: each recognized file kind (project, gcode) on the evidence read draws the kind error before resolution; image and snapshot kinds serve as Display content; a malformed ref and an unrecognized kind discriminant each draw unknown-ref, never the kind error (asserted distinct).
5. Session resolution: an unknown or deleted session draws unknown-session before any delegate call, for every tool.
6. Verbatim relay: a structured error from each delegate arrives in the tool result with cause fields intact (asserted per delegate); a success payload round-trips the tool's JSON schema; the fileindex no-upload answer relays as its distinct third shape — an answer, never an error and never content — so the agent's ask-for-the-project behaviour has its observable (asserted); fileindex's view kind error and unknown-ref each relay verbatim, asserted distinguishable from each other and from `mcp`'s own evidence-read kind restriction (asserted).
7. Snapshot flow: gating parameters passed (requester Agent; the agent-requested camera carried straight through as the printer-state contract's bare per-call identifier, else the stored choice — both asserted on the faked surface, nothing camera-shaped validated or fabricated in `mcp`), success attaches and returns the reference, each refusal in printer-state's partition relays distinctly — no-telemetry on an evidence-only printer, unknown-camera on an agent-named undiscovered camera, the discovery-failure unreachable error, the two agent-gating reasons, out-of-scope on a stored choice, no-camera, and the verbatim-bound unknown-printer answer (asserted per reason) — and nothing attaches on refusal; `attach_snapshot`'s capture-failed answer — a healthy `sessions`' validity answer, camera-named — relays verbatim, asserted distinct from `attach_fault`'s system fault class (which is never camera-named).
8. Catalog completeness and call validity: every declared tool resolves to a real delegate call and every schema round-trips (enumerated over the catalog as data); an unknown tool name and schema-non-conforming arguments each draw their structured validity rejection naming the tool or mismatch — never a transport error (asserted), while the same call on a revoked token draws the credential rejection instead (token resolution first — asserted), a real tool with non-conforming arguments on a deleted session draws unknown-session (session resolution before schema validation — asserted), and an unknown tool on a deleted session draws the unknown-tool rejection (no session semantics for a non-operation — asserted); no caching — two identical calls each reach the delegate, and a value changed between them is served current on the second (asserted); every bounded-view tool's continuation round-trips the tool surface — a truncated result's marker feeds the continuation parameter and the next page arrives, and a refused continuation relays as its distinct answer, never an empty page (asserted per bounded-view family); a ref-addressed `.3mf`/gcode view call reaches the named upload even against a shared filename, an unqualified call the newest of its named kind — the both-kind tools' schemas rejecting an absent ref with no kind (asserted per kind), the diff tool's two same-kind refs round-tripping, and the runtime mismatch rejections — differing-kind diff operands, and a `kind` argument disagreeing with a supplied ref — each drawing the structured validity rejection naming the mismatch (asserted); the log views' boundary-unknown indication and the log/config reads' provenance survive the declared schemas into the tool result (asserted on content); statelessness — a full pass over the catalog makes zero transcript writes (asserted on the faked `sessions`); provenance on telemetry and evidence results survives the relay into the tool result intact (asserted on content); validity answers produce no log line, while each endpoint-store fault logs its operation name (asserted).

Failure-mode tests (`test_failure_<dependency>_<mode>`):

- endpoint store: `unavailable` (provisioning fault per the message-lifecycle line), `resolution_read_fault` (a store fault during the per-request token check draws the retryable fault-class error — never the credential rejection), `write_failure` (revoke re-drivable), `corrupt_row` (a retryable fault-class error, logged — never the credential rejection, whose validity answer has a different remedy), `stall` (bounded, injected), `race` (an injected revoke racing a provisioning call: both land whole in some order and the revoked record is never overwritten live — a torn-down session is never left holding a live endpoint, per the message-lifecycle contract's serialization rule — asserted).
- sessions: `binding_read_fault` (the failure surface relayed, never a binding state), `resolution_fault` (structured, not unknown-session), `evidence_read_fault` and `list_fault` (read-failure relayed verbatim, distinct from unknown-ref), `evidence_reproduction_fault` (the evidence contract's derivative-reproduction fault class naming the file — relayed distinct from read-failure and from unknown-ref, never collapsed), `attach_fault` (the system fault class, never camera-named — capture-failed, the healthy validity answer, is contract test 7's, not a failure mode), `camera_choice_read_fault` (the failure surface relayed structurally, like the binding read), `stall` (bounded, injected — the conventions' standard injection for this dependency too); each fault case asserts its log line carries the tool name and session, and the credential rejection its session where known.
- fileindex: `view_fault` (read-failure relayed verbatim), `render_fault` (a mesh-render failure relayed with its upload and viewpoint named, verbatim), `stall` (bounded, injected) — and the out-of-range window, a healthy validity answer, joins contract test 6's relay assertions, distinct from every fault; fault log lines assert the tool name and session, here and on the printer bullet alike. The validity answers — the view kind error and unknown-ref, each asserted distinguishable from each other and from `mcp`'s *own* evidence-read kind restriction (two different kind errors with different remedies, never collapsed) — join contract test 6's relay assertions.
- printer: `telemetry_fault`, `log_fault`, `config_fault`, and `snapshot_fetch_fault` per cause category (connection, timeout, protocol — each relayed with its cause, the fetch fault distinct from every refusal), `stall` (bounded). The healthy closed-set answers — NoTelemetry, unknown-printer, unknown-section, and the snapshot refusals — are contract tests (items 3 and 7), not failure modes: they are normal answers of a healthy dependency.
- randomness: `exhausted` (provisioning fails structured, never a weak token). (The listener-address value is fixed at wiring with no reachable runtime failure — no failure mode exists for it, deliberately.)

Provisional mocks — unverified: none. The MCP wire framing is exercised by integration tests against the real server; whether the *adapter* accepts a streamable-HTTP server is `agent`'s release item.
