## 1. Purpose

Session lifecycle and store, per the architecture. This module owns the seam behaviour the evidence and binding contracts define, the `sessions` side of the message-lifecycle contract, the `sessions` emitter of the events contract, and the stored camera choice whose capture-time semantics the printer-state contract owns; this document covers what stands behind those — storage, private structure, error handling — plus the session-store operations no contract claims (below).

## 2. Internals

- **Store** — the module's tables in the shared SQLite database: sessions (id, name, archived, deleted tombstone — the flag whose commit makes the session atomically unknown-session per the conventions' deletion rule — turn state, created); a per-session *commit sequence* spanning every session-scoped durable mutation — transcript entries, binding, name, archive, camera choice, and evidence-row commits alike (distinct from evidence's per-kind identity sequence) — which is what makes cross-kind replay order reconstructible; transcript entries (session, entry key, kind, structured payload, commit sequence); evidence rows (session, kind, identity sequence, commit sequence, origin metadata, on-disk paths for original and derivative) — carrying both numbers: the per-kind identity sequence behind the ref and the cross-kind commit sequence like every other durable mutation; bindings (stored name, manual flag, intake-order cut-off); the last-announced derived binding output; the camera choice (camera plus its recorded scope — the offering printer's canonical name and URL, per the printer-state contract); and the re-drive journal covering deletion, intake, *and creation* — a creation journals its session id before anything else runs, which is what gives the startup residue scan an enumerable input for crashed creations. The stuck-entry set behind the persistence-failure condition is deliberately *not* a table: it is in-memory state, necessarily, since the condition exists exactly when this store is refusing writes; a restart during the condition loses the stuck content within the message-lifecycle contract's accepted-bounded-loss, the user-message entry alone surviving via `agent`'s backstop and restoration. Session search is an FTS index over names and transcript text. Every observable all-or-nothing rule in the contracts maps to one transaction here.
- **Evidence intake pipeline** — validate (images in-module; `.3mf`/gcode via `fileindex.validate_and_index`), produce the image derivative, then commit row + files + index membership in the journaled two-phase step the evidence contract's crash window describes; the sequence number is allocated inside the commit, which is what makes rejected and crash-aborted intakes number-free.
- **Image pipeline** — decode (JPEG, PNG, HEIC via a native decoder), apply EXIF orientation, re-encode the bounded derivative. A derivative is produced exactly where the evidence contract's Display rule requires one — a browser- or model-unconsumable original, or one over the size bound; an image needing none commits without one, so a derivative fault can only reject an intake whose derivative is required. Orientation is applied before re-encoding because the derivative-fidelity rule forbids relying on metadata surviving; reproduction-at-read reuses the same pipeline.
- **Binding derivation** — a pure function from (stored binding, newest post-cut-off named upload via `fileindex.printer_name`, `printers()` result) to the binding contract's closed set, plus the emission comparator against the last-announced output. When the function's outcome is an auto-bind, re-derivation commits the contract's one derived write — canonical name, manual flag unset, cut-off moved — in the same transaction as its announcement. Re-derivation runs on upload commit, bind, each freshness event, startup, and a bounded re-attempt timer that exists only while an input is faulting; it skips tombstoned sessions — a freshness event racing a deletion re-derives nothing and emits nothing for that session, per the conventions' deletion rule.
- **Domain instructions** — static instruction assets composed into the `instructions` argument of `agent.send`: the finding → evidence → change structures with certainty registers, the ask-for-the-`.3mf` behaviour, OrcaSlicer-guided calibration, and the evidence-quality pattern, whose actionable ask is the *evidence-request* markup kind (R5, R8, R9). Two typed markup kinds exist, both instructed and both parsed: *finding* — the finding → evidence → change structure, each claim tagged with one of the three certainty registers (established, hypothesis, external) — and *evidence-request*, naming what a usable shot looks like. A markup parser turns streamed text carrying either kind into its parsed content carried *within the text-segment entry's structured payload* — never a new entry kind, since the events contract's entry-kind set is closed; the payload distinguishes the two kinds, which is what `ui`'s two renderings key on. Unparsed text commits as a plain text segment (the fallback that makes non-emission visible only through the release item).
- **Persistence-failure condition** — a retry queue over stuck entries (the in-memory set above) with the aggregation, causality-hold (a turn's entries queue behind its stuck user-message entry), and clearing rules the message-lifecycle contract states; the condition and each session-failure event carry the underlying store failure's cause, named per R10, alongside the key-set; each key-set change emits the event, and the user-message entry's landing confirms to `agent` via `message_landed` — the only thing that clears the pending-message backstop. A confirmed deletion supersedes a standing condition: the stuck set is discarded with *no clearing event* — session-deleted is the terminal — and the condition gates nothing while it stands: sends and retries proceed per the contract.
- **Retry** — the flag answers busy; otherwise `retry` delegates to `agent` on the persisted message (nothing-to-retry is `agent`'s synchronous answer from the pending store's recorded outcome, relayed as-is); the retried turn reuses the original message key, its new entries correlating to it, and `sessions` commits no transcript entry at retry acceptance — the turn-state flip is the one durable write, the entries arriving through the sink like any turn's. Plain `send` commits its user-message entry *after* acceptance, in the same commit as its flag flip, emitting the entry's event then — a synchronous rejection therefore leaves nothing, and a post-acceptance store failure raises the condition per the contract's asynchronous line, never a synchronous error.
- **Deletion cascade** — journaled ordered steps: session tombstone commit, `agent.teardown`, evidence file removal, `fileindex.remove_session`, row removal; re-driven at startup and by bounded live re-attempt.
- **Prompt assembly** — `send` resolves every attached ref before acceptance: an unresolvable value is the synchronous unknown-ref rejection, unservable content the read-failure or derivative fault-class rejection, a ref count over the per-message cap the cap rejection, and a message with no text and no ref (no attachment, at creation) the empty-message rejection — all at the action site per the evidence and message-lifecycle contracts. `create_with_first_message`'s attachment is raw bytes, not a ref: it runs the evidence intake pipeline, and an intake-validation rejection rejects the creation whole per the message-lifecycle contract's distinct first-message-attachment rejection. Image refs contribute Display content labelled with their identifiers, file refs their handles, composed with the text into `agent.send`'s `content`; the instructions travel in its separate `instructions` argument per the Domain-instructions bullet.
- **Session creation** — `create_with_first_message` validates first (the synchronous rejection families; the attachment's intake validation against its route-declared kind — the evidence contract's surface-owned declaration, `server`'s route declaring it and `sessions` never re-deriving it), then journals the new session id, then commits the session row, the user-message entry, and the attachment's evidence intake (the intake pipeline's journaled two-phase step running as part of this pre-acceptance work) — this is the contract's *pre-acceptance* storage, so a failure here is the synchronous storage rejection, nothing standing but the journal entry, which the unwind clears — then issues the creation-context first `agent.send` (the message-lifecycle contract's rule: provisioning and backend creation ride it; its synchronous rejection, a provisioning fault included, unwinds everything committed — the row, the entry, and the attachment's intake whole (evidence row, files, index membership, through the intake journal's unwind, residue-free per the evidence contract) — and runs `agent.teardown` for any backend residue before the rejection returns: nothing persisted anywhere, per the sync line), and on acceptance completes the journal entry in the same commit as the turn-state flip, emitting the session-created and entry events then and confirming `agent.message_landed` immediately — the first message's entry committed *before* acceptance, so its landing confirmation fires the moment the pending row exists, and the backstop never restores a first message that already landed. The session id reaches the caller only with acceptance, and `list`, `search`, and the FTS index all exclude a session whose creation journal entry is incomplete — the pre-acceptance row is unobservable through every surface, id-addressed and enumerated alike; sink events for the accepted turn find the committed row by construction. A live failure of the post-acceptance completion commit is asynchronous per the contract and re-drives bounded like any journal step. The unwind is symmetric: a creation that fails *after* provisioning succeeded — a store fault on the session or transcript commit — runs `agent.teardown` for the half-created session as part of rejecting the creation whole (teardown is idempotent cleanup and internally revokes the endpoint, per the message-lifecycle contract), so no live endpoint outlives a session that never existed — the same vehicle the deletion cascade uses, never a direct `sessions → mcp` call, which is not an architecture edge.
- **Startup recovery** — the scans the message-lifecycle contract's composition rules order after wiring: pending-message restore via `agent.pending_message`, drained by repeated call-and-land until it answers `None` (the contract's drain rule), each restore first checking the message key against committed entries — an entry that already landed is never re-committed, its unlanded row healed by confirming `message_landed` instead; residue resolution over the creation journal's incomplete entries, decided by `agent.pending_message` per destruction-on-certainty — the pending row is written *at acceptance*, so it is the accepted/not-accepted discriminant (`backend_state`'s row is written before acceptance and cannot be): a definite no-pending answer means the send was never accepted — the unwind runs (`agent.teardown`, idempotent, then local removal of the row and entry, per the contract's before-acceptance crash arm); a pending row means the creation was accepted and stands — the journal entry completes *and that completion commit sets the turn flag true* (the deferred acceptance flip, which is what lets `agent`'s synthesized interrupted terminal apply rather than be dropped); the error arm preserves everything for the next scan, destroying nothing on unknown state; intake journal replay (crash-torn intakes settle first); cascade re-drive; and last the re-derivation pass over all sessions (the announce-at-startup rule) — last so every announcement derives from settled intakes, never a crash-torn one.
- **Name derivation** — local, no model call: the first message's leading text, trimmed and truncated; with no text, the attachment's kind and time (R4's fallback).
- **Session state operations** — rename (a trimmed-empty name rejected synchronously, like `bind`'s rule), archive/unarchive (flags filtering the default list and search per R4; orthogonal to every standing condition), and the camera choice set/read (the set records the choice with its scope as supplied from the offering discovery; capture-time validation is printer-state's). Each change emits its durable event (name changed, archive changed, camera choice changed) with the state-bearing payload; the FTS index updates with renames and transcript commits.
- **Sink commitment** — the message-lifecycle sink events become the events contract's entry kinds at commit: `Text` accumulates into text segments (deltas re-emitted as ephemerals carrying the segment's entry key) — a segment closes at the next non-Text sink event or the turn terminal, whichever comes first, preserving arrival order; a bounded flush commits the *same entry* meanwhile, under its one stable key with grown text — one entry per segment always, its entry-appended event re-emitted state-bearing on each flush, the events contract's keyed dedup rendering it once — so a crash loses at most the last flush window (the contract's partial-text-kept) and a delta's key always names the entry its durable form carries, `ToolCall` commits its structured payload and `ToolResult`'s commits verbatim, never flattened (the contract's rule), `Failure` commits the failure entry, `ResumeFired` a system note; every entry gets its transcript-owner-minted entry key, correlated to the turn's message key, and each committed entry emits its entry-appended durable event. A sink event kind outside the vocabulary is dropped and logged, never committed; events for a session with no committed row — deleted (deletion permanence) or never committed alike — are dropped whole; and a synthesized terminal whose message key already has a committed terminal entry is dropped — deduplication is by key against committed entries, never by the flag, so a turn whose flag flip was lost to a store fault still gets its recovered terminal.
- **Turn state** — accepted-to-terminal per session, persisted with the session row: flipped at acceptance and at each terminal, emitted as the turn-started/turn-ended ephemerals, carried as the turn-in-flight flag on every session-scoped durable payload (session deleted excepted, per the events contract's key-only exception) and on state-fetch responses. Each terminal's commit also confirms `agent.turn_landed(session, key)` — fired at the failure entry's commit for a failed turn, and at the success terminal's flag-flip commit for a successful one (`TurnEnd` commits no entry, but its flag flip is a commit) — the contract's terminal-landing confirmation, which is what lets `agent` finalize the turn's persisted state. The message-lifecycle contract's *busy* rejection is enforced twice, identically: the flag answers it for send and retry, and `agent`'s one-turn lock answers it for what the flag cannot yet know — chiefly the window between an automatic resume's acceptance at `agent` and the `ResumeFired` commit that flips the flag here (the flag flips at `sessions`' own acceptance for send and retry, and at the `ResumeFired` commit for resumes) — either path returning the same structured busy answer, relayed as-is.
- **Event emitter** — an in-process multi-subscriber channel; per-session commit sequence numbers give the events contract's commit order; ephemerals fan out unbuffered with their session keys.

## 3. Interface

The public surface is what the contracts define: evidence, binding, the message-lifecycle operations owned here, the emitter seam, and the session-store contract's operations (`list`, `search`, `transcript`, `session_state`, `delete`, `rename`, `archive`/`unarchive`, `resolve`, and the camera-choice set/read) — every signature, rejection, and paging rule theirs, realized here, nothing defined here. The transcript and state fetches serve from the store's committed entries and session row (payloads verbatim, commit order via the commit sequence; the state fetch carries the turn-in-flight flag and any standing session-failure condition). Module-private interfaces exposed to tests directly: the journal (begin/complete/scan), the instruction-asset loader, the derivation function, the emission comparator, the markup parser, the name-derivation function, and the clock behind every bounded re-attempt timer and stall bound (injected — no test waits on real time).

## 4. Error handling and failure visibility

Errors follow the conventions: structured, cause-naming, fault-class never conflated with validity. Per failure mode, what is visible: store faults name the operation and surface as the failing call's error arm (or the persistence-failure condition for accepted turn content); intake unwind failures re-drive and log each attempt; a faulting derivation input logs the input and starts the re-attempt timer; cascade step failures log the step and re-drive — the session is already unobservable from the tombstone commit (per the conventions' deletion rule), so the trouble is visible only in the log, never as a lingering session. Image-pipeline faults (decode, derivative, reproduction) log the file and stage alongside their structured rejection; a startup-scan failure logs the scan and stands until its bounded re-attempt completes, the service serving throughout. The remaining declared modes are visible the same way: relayed `agent` rejections surface on the caller's answer; teardown and `message_landed` re-drives, `fileindex` removal and internal faults, and `backend_state`/`pending_message` error arms each log the operation, session, and cause per occurrence and re-drive; the printer subscription's duplicate deliveries are absorbed silently by design (idempotence is the assertion), while the startup re-derivation pass logs each divergence it corrects after missed events. Everything logs through the service log with session and entry/evidence identifiers; nothing is swallowed.
